1. 背景与问题

工程背景

民用航空电子系统中，ARINC 615A 是标准化的数据加载协议（基于 TFTP/UDP）。设备在交付和维护时需通过数据加载器（DLS）对目标硬件（THW）进行软件/数据装载。

核心问题

当前验证多停留在 项目级 ICD 功能测试 层面，缺乏对 协议级符合性 的系统化验证手段。

  • ICD 测试只验证"能不能用"，不验证"是否符合标准"
  • 缺少可控的、可重复的负面测试（mutation）能力
  • 现有工具多为单向（仅 DLS 或仅 THW），无法自环验证
协议符合性验证能发现 ICD 测试无法覆盖的边界行为（如块号回绕、选项协商失败、状态码异常），是 ICD 测试的补充而非替代。

2. 研究问题与目标

研究问题 (RQ)

"如何构建一个可控的双角色（DLS/THW）仿真环境，基于 TFTP 和 ARINC 615A（含最小 ARINC 665 支持），系统化地暴露协议级的符合/不符合行为——超越项目级 ICD 的逐点检查？"

核心主张

一个角色可切换的仿真器 + 显式验证点/判定模型 + 变异式负面用例，构成一套可复用的 符合性验证方法，而不仅仅是单侧的加载器或目标桩。

双角色设计使得同一工具既能当 DLS 也能当 THW，可在单机上完成自环测试（loopback），无需等待真实硬件到位即可开展验证实验。

4. 关键设计决策及理由

决策选择理由
角色设计双角色可切换单机自环验证，不依赖外部硬件；同一协议核心复用于两端，减少实现不一致风险
实现语言Python 优先快速原型迭代；标准库含 TFTP 基础；后续可选 C/C++ 优化热路径
665 范围最小支持仅需 .LUH 构建/校验和 THW ID 检查即可支撑判定；完整 665 超出符合性验证必要范围
验证策略自环 + 变异验证自环验证基本功能正确性；变异验证验证能否检出已知不符合行为；无需真实硬件即可证明方法有效
保密处理论文用通用术语DLS/THW 等通用名称用于公开文本；OHMS/IDU 等内部名称仅存于私有笔记

5. 软件架构设计

分层架构

L4 场景引擎 → 故障注入 → 判定/报告

L3 ARINC 615A 会话层（虚拟文件状态机）

L2 ARINC 665 LSAP 编解码（最小）

L1 TFTP 核心（RFC 1350 + 选项 + 回绕→1）

L0 UDP 网络 I/O

核心设计贡献

Role Controller（角色控制器）

同一套协议核心引擎，通过角色切换在 DLS 模式与 THW 模式之间切换。

优势：

  • 两端行为一致，减少实现偏差
  • 自环测试只需一个进程
  • 测试覆盖两种角色分配
角色无关的协议核心是本方案的核心创新点：传统工具分别实现 DLS 和 THW，容易出现两端理解不一致的问题。

9. 为什么这样规划与实施？

① 为什么是"符合性验证"而非"功能测试"？

功能测试回答"设备能否正常工作"；符合性验证回答"设备是否遵循标准"。前者是项目需求，后者是行业标准要求。两者互补，但层次不同。

② 为什么双角色而非单侧工具？

单侧工具需要真实对端才能测试；双角色设计允许自环验证，加速开发迭代，且能系统性覆盖两端行为。

③ 为什么变异验证？

仅验证"正常情况通过"不能证明工具有效。通过注入已知缺陷（坏校验值、错误块号、忽略选项），验证工具能正确判定 Fail，才能证明验证方法的可信度。

④ 为什么 Python 优先？

Phase 0 目标是验证方法可行性，不是生产部署。Python 的快速迭代能力让我们聚焦协议逻辑而非内存管理。性能热点可后续用 C 替换。

⑤ 为什么最小 665 而非完整实现？

符合性验证的核心在 615A 会话层。665 仅需足够支撑判定（.LUH 构建、校验值、THW ID），完整实现超出本研究必要范围。

⑥ 为什么论文与代码分离？

代码追求"能跑"，论文追求"能论证"。分离避免代码里程碑被写作需求拖累，也避免论文变成"开发日志"。两者通过共享的验证点和实验结果连接。

10. MVP 完成标准

最小可行产品 (MVP) 定义

  1. 自环 Operator DOWNLOAD（标称场景）在两种角色分配下均 Pass
  2. 至少 4 个变异用例 正确判定 Fail 并给出清晰原因
  3. 最小 LSAP 校验值错误被正确拒绝/标记
  4. 每次运行产出机器可读报告（JSON）
  5. README 记录 <10 步即可运行自环测试
MVP 标准聚焦于"方法是否可行"而非"功能是否完整"。5 条标准覆盖了正向验证、负向验证、判定可信度、可重复性和可用性。
