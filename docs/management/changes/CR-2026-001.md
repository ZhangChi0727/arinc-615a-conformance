|---|---|
| **Change class** | Baseline |
| **From** | RB-2026-001-v4.1 |

| **Required approval** | Independent methodology review and RG6-style claim review |

## Trigger and problem

The v4.1 scope includes timeout, retry, sequence, timing-bound coverage, and
monotonic timestamps, but its formal core does not fully define real-time
traces, clocks, measurement uncertainty, or boundary verdicts. This gap can
make an implementation use exact point thresholds despite nonzero clock,
timestamp, scheduler, capture, or path uncertainty.

## Decision and affected semantics

v4.2 adds:

- an explicit distinction among logical order, deterministic real time,
  run-order dependence, and latent temporal dynamics;
- timestamped traces and a clock-augmented observable EFSM;
- trigger/response/cancellation/silence and clock-reset semantics;
- observation intervals derived from a reviewed measurement-error budget;
- PASS by interval containment, FAIL by disjointness, INCONCLUSIVE by partial
  overlap, and ERROR for an invalid timing instrument;
- timing partitions, fault operators, held-out timing-fault evaluation, and
  order/clustering/drift analysis;
- co-located Chinese translations in key controlled documents.

The change does not introduce a stochastic protocol kernel. DTMC/HMM remains
outside the core baseline.

## Impact and migration

Affected artifacts include the methodology report, baseline declaration,
research/experiment/engineering plans, CRS and trace schemas, applicability,
evidence manifest, architecture, terminology, review gates, risks, claims, and
repository validation. Existing evidence recorded under v4.1 is not relabeled.
Any timing claim must be re-executed or re-evaluated under v4.2 with sufficient
clock metadata and raw timestamps.

## Alternatives considered

1. Keep v4.1 and treat time informally — rejected because it leaves boundary
   verdicts under-specified.
2. Introduce HMM/DTMC timing — rejected because protocol order, measurement
   variability, and latent fault dynamics are different objects.
3. Use point thresholds with a tolerance — rejected because tolerance without
   a traceable error budget is arbitrary.

## Required verification

- English/Chinese report structure and mathematics match.
- Numeric equations remain (1)–(14); timed equations are (T1)–(T5).
- Every active baseline reference uses v4.2.
- No parallel Chinese report file remains.
- Local links, Markdown fences, baseline validator, and test suite pass.
- Independent reviewers inspect timing semantics, error-budget rules, and
  claim wording before approval.

## 中文版

### 触发问题

v4.1 已把超时、重试、序列、时序边界覆盖和单调时间戳纳入范围，但未完整定义实时时戳迹、时钟、测量不确定性和边界判定，可能导致工具在存在非零时钟、时间戳、调度、捕获或路径误差时仍使用精确点阈值。

### 决定

v4.2 区分逻辑顺序、确定性实时时间、运行顺序依赖和隐含时序动力学；增加带时戳迹和带时钟 EFSM；定义触发/响应/取消/静默、时钟复位及误差预算；观测区间包含于允许区间时 PASS，不相交时 FAIL，部分重叠时 INCONCLUSIVE，仪器无效时 ERROR；增加时序分区、时序故障、留出评价和顺序/聚类/漂移分析。核心不引入 DTMC/HMM。

### 迁移与批准

v4.1 证据不得改标为 v4.2。任何时序主张必须具有足够时钟元数据和原始时间戳后重新执行或评价。合并前必须完成中英文结构/数学一致性、公式编号、v4.2 引用、链接、Markdown、验证脚本和测试检查，并由独立方法评审者检查时序语义、误差预算和主张措辞。
