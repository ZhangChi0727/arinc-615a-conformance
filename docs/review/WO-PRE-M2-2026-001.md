# WO-PRE-M2-2026-001 — Pre-M2 execution checklist

This checklist supersedes its earlier execution instructions under CR-2026-007
and DD-023. Historical versions remain in Git. It is not an approval or authority
to merge, establish a capability or start M2. README and project-status.json remain
the current status entry points; no separate HANDOFF or procurement tracker is needed.

## Track A — Complete independent M1 review

1. Finish the candidate corrections and all local and remote three-version CI checks.
2. Obtain named independent RG0 and RG1 review of the complete branch range, bound
   to its final unchanged 40-character Head. Old-Head outcomes do not transfer.
   Review includes historical source editions, bilingual semantics and the bounded
   protocol/infrastructure division. Any Must finding requires REWORK.
3. After approval, add no commits. With user authorization, move from Draft to Ready
   and perform an ordinary merge with exactly two parents. Verify its second parent
   equals the approved Head and its tree equals the approved tree.
4. Wait for successful main CI on the merge SHA, then clean the temporary branches
   and verify protection. Do not create a tag or a post-merge status-only commit/PR.
5. Approval and merge facts reside in the GitHub review and Git history. Pending
   fields in the approved candidate are not rewritten after approval. A later
   authorized substantive PR may record those facts and close the change record.

## Track B — Preserve the bounded dispositions

P2/P3/P7 identities are registered, without establishing network capabilities.
The selected Compliant Network does not use P3-specific deviations; AFDX remains
unselected and deferred. The applicable IPv4/UDP host service is an explicit
unestablished infrastructure prerequisite, not a complete RFC inventory or a
claim about an implementation. Plan substantiation before execution Configuration.

The CR action table controls remaining direct 615A/665 refinement, option edges,
extra timing analysis, requirement classification and editorial label work.
Deferred actions are not CLOSED. FIND and AFDX deferrals and the bounded 665
exclusions are retained; changing their scope needs a new reviewed decision.

## Track C — Sources and unresolved dependencies

Public RFC copies remain outside Git with retrieval identities. RFC 1122 is
distinct from RFC 1123; receipt does not establish compliance with the historical
RFC or its later updates. ARINC 645 remains open and its four capabilities remain
NOT-ESTABLISHED. P7's future AID supplement, addressing alternatives and deployment
details remain conditional review topics, not automatic acquisition mandates.
No source receipt by itself clears blockedBy or establishes a capability.

## Track D — Separately authorize M2

Only after Track A closes, prepare and review a new M2 work order and change record.
It must cite the exact approval/merge/CI evidence, choose the admitted model and
infrastructure tasks, and carry forward deferred actions explicitly. M1 exit alone
does not authorize M2, Configuration, execution or any conformance claim.
Update README/JSON and roadmap/gate state coherently in that substantive PR;
do not prescribe an ad hoc lifecycle state outside the controlled vocabulary.

# 中文版

本清单在 CR-2026-007 与 DD-023 下替代旧执行要求，历史版本由 Git 保留。
它不构成批准、合并授权、能力建立或 M2 启动许可。README 与 project-status.json
仍为当前状态入口；不另建 HANDOFF 或采购跟踪文档。

## 路线 A——完成独立 M1 评审

1. 完成候选修正、本地检查及远端三版本 CI。
2. 具名独立评审者对完整分支范围执行 RG0/RG1，绑定最终不变的 40 位 Head。
   旧 Head 结论不继承；复核历史版次、双语语义及协议／基础设施边界。
   任一 Must 均要求 REWORK。
3. 批准后不再提交；获用户授权后转 Ready，普通合并并验证恰有两个父提交，
   第二父等于批准 Head、合并树等于批准树。
4. 等待 merge SHA 的 main CI 成功，清理临时分支并核验保护。
   不建 tag，不增加专门 post-merge 状态提交或 PR。
5. 批准与合并事实由 GitHub Review 和 Git 历史承载，不改写已批准候选的 pending 字段。
   后续获授权的实质 PR 可记录这些事实并关闭变更记录。

## 路线 B——保留有边界处置

P2/P3/P7 身份已登记，网络能力未建立。已选择 Compliant Network，不采用 P3 特有偏差；
AFDX 未选择且延期。适用 IPv4/UDP 主机服务为显式未建立基础设施前提，
不是完整 RFC 清单或实现主张；执行 Configuration 前须规划其验证。

CR 行动表控制 615A/665 直接精化、选项边、额外时序分析、需求分类和编辑性标签工作。
延期不等于 CLOSED。保留 FIND、AFDX 延期和 665 有边界排除；范围改变须有新受审决策。

## 路线 C——来源与未决依赖

公共 RFC 副本保存在 Git 外并登记获取身份。RFC 1122 与 RFC 1123 不同；
取得副本不建立历史 RFC 或后续更新的符合性。ARINC 645 仍开放，四项能力保持
NOT-ESTABLISHED。P7 未来 AID 补充版、寻址替代和部署细节仍为条件评审事项，
不是自动采购要求。接收来源本身不得清空 blockedBy 或建立能力。

## 路线 D——另行授权 M2

路线 A 闭合后才能另编并评审 M2 工作单与变更记录。引用精确批准／合并／CI 证据，
选择纳入的模型与基础设施任务，并显式承接延期行动。M1 退出不自动授权 M2、
Configuration、执行或符合性主张。在实质 PR 中一致更新 README/JSON 与路线／门禁状态，
不另造受控词汇之外的生命周期状态。
