## Problem

The released v4.3 tree correctly preserves its pre-handshake state, including
`NOT-DETERMINED` compatibility. Method-repository PR #15 subsequently completed
the third handshake against that immutable release and recorded a reviewed,
qualified compatibility disposition. This repository must acknowledge that
later external disposition without rewriting v4.3 history, confusing the method
definition with the disposition record, or implying that an instance evaluation
or Project Configuration now exists.

## Controlled identity chain

| Identity | Controlled value | Meaning |
|---|---|---|
| Method definition | `48dd8232b7efe6b0dba3fcb75dfc154d034d2b0b` | Immutable Candidate GVS Core definition used by the ARINC mapping |
| Method compatibility disposition | `c02330d21fe2d3e89e7e2d6352872d52461a6dda` | Ordinary merge of method PR #15; records the activated reviewed disposition |
| Approved method PR head | `37fb88329abaea8f7127da96a66c0ac5d7525543` | Exact second parent of the method merge and exact head covered by natural-person approval |
| ARINC source release | `523d42bf03a1135b3d63a00bfb47d3b879d3927e` | Immutable v4.3 release content assessed by the method repository |
| ARINC source tag | `v4.3` | Annotated release tag for the assessed ARINC source release |
| Candidate acknowledgement | `RB-2026-001-v4.3.1` | This repository's controlled acknowledgement candidate; not yet a release tag |

The two method commits are not aliases: the definition commit supplies the
method contract, while the disposition commit supplies the reviewed result of
applying that contract to the immutable ARINC v4.3 source. Neither may be
replaced by a branch name, a mutable `main` link, or the future ARINC merge SHA.

## Approved change scope

1. acknowledge the method-side disposition as
   `REVIEWED-COMPATIBLE-WITH-QUALIFICATION`;
2. preserve every R01–R18 and A01–A07 relation and row status exactly;
3. bind the acknowledgement to the immutable v4.3 release and both immutable
   method identities;
4. carry Q-01–Q-09 as mandatory limitations;
5. keep instance evaluation `NOT-EXERCISED` and Project Configuration
   `NOT YET ESTABLISHED`;
6. establish `RB-2026-001-v4.3.1` only as a candidate until independent review
   approves an unchanged head and an ordinary merge completes;
7. create annotated tag `v4.3.1` only after approval and merge; do not create a
   method-repository baseline or tag.

This change does not modify equations 1–14, T1–T5, robust timing semantics,
protocol conformance conclusions, evidence populations, generic Core content,
or the v4.3 release tree.

Activation requires a named independent reviewer to approve an unchanged final
PR head, followed by an ordinary two-parent merge whose second parent is that

deletion follows release verification.

Automated checks validate repository-side identities and invariants; they do
not manufacture natural-person approval, compatibility evidence, instance
evaluation, certification credit, or authority acceptance.
